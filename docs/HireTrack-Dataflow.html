HireTrack data flow

How data moves through the production build: the browser talks to one gateway, eight Spring Boot services each own their data, Kafka carries events between them, and only ai-service and job-feed-service reach outside. Pick a flow to highlight it.

Browser / gateway HTTP Internal REST (/internal, X-Internal-Token) Publishes event (via outbox) Consumes event External API call Data the service owns

Arrows point from the side that starts the exchange: the caller for HTTP, the publisher for events, the topic for deliveries to consumers. Responses come back the same way. "No consumer" topics are published in v1 so future services can subscribe without changing the producer.

The five main flows

1 · Sign-in

  1. Browser posts credentials to /api/v1/auth. The gateway forwards them to identity-service.
  2. identity checks the bcrypt hash and counts failed logins in Redis (5 per email per 15 min).
  3. It returns a 15-minute RS256 access token (kept in memory) and a rotating 7-day refresh token in an HttpOnly cookie, saved in refresh_tokens.
  4. The gateway verifies every later token with identity's JWKS public key.
  5. user.registered / user.seen go to identity-events. job-feed records activity so it only plans feeds for users active in the last 14 days.

2 · Resume

  1. Browser uploads a PDF (max 2 MB) or pastes text to /resumes.
  2. resume-service extracts PDF text with PDFBox and stores the original PDF in S3 (S3Mock locally).
  3. The new resume becomes active; the previous one is deactivated, never overwritten.
  4. resume.activated is published to resume-events in the same transaction (outbox).

3 · AI match

  1. Browser posts a job description to /matches with an Idempotency-Key.
  2. match-service fetches the active resume from resume-service (/internal/users/{id}/active-resume).
  3. It calls ai-service /internal/match. ai checks the 20-per-day quota in Redis, then calls OpenAI (or Claude) with a strict JSON schema, behind a bulkhead and circuit breaker.
  4. ai records the result by requestId and one ai_usage row per paid call.
  5. match stores score, missing skills and bullets in matches and publishes match.completed.

4 · Pipeline & dashboard

  1. Browser creates or moves applications through /applications; stage changes use If-Match (optimistic locking).
  2. Saving from a match makes application-service read company and role from match-service (/internal/users/{id}/matches/{id}).
  3. Every change publishes application.* or interview.* to application-events.
  4. analytics-service consumes them, skips duplicates via processed_events, applies only newer versions to its projections and clears that user's Redis cache.
  5. /dashboard answers from the projection, cached per user and timezone.

5 · Daily job feed

  1. The planner (one pod, ShedLock, every 5 min) creates a feed_runs row for each due user and publishes feed.run-requested. "Refresh now" does the same, once an hour.
  2. Workers consume feed-commands, fetch the active resume and search Adzuna. Users with the same search share one fetch through a Redis cache and lock.
  3. Postings are upserted, already-seen ones skipped, and the top 15 by word overlap kept.
  4. The submitter sends them to ai-service /internal/feed-batches (provider Batch API); the poller applies the scores to feed_items and publishes feed.ready.
  5. "Save to pipeline" calls application-service /internal/users/{id}/applications to create a Wishlist application.

Producers write events into an outbox table in the same transaction as their own data, and a relay publishes them to Kafka. Consumers retry 3 times, then send the record to <topic>.DLT.

Each service has its own schema and database user, with no foreign keys across services. The shared platform tables live in each schema that needs them: outbox (event producers), processed_events (event consumers) and idempotency_keys (services with creating POSTs).
